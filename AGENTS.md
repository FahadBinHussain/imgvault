# imgvault

chrome extension (mv3, no build for ext itself; vite build outputs to `dist/`) + tauri rust native host for yt-dlp downloads.

- native host source: `native-host/src-tauri/src/main.rs`; build with `cargo build --release --target x86_64-pc-windows-gnu` and copy the exe to `native-host/ImgVault-Native-Host.exe`; rebuild + copy after every rust change, not just compile.
- extension edits: bump `"version"` in `nextgen-extension/public/manifest.json`, run `pnpm build`, then `start msedge http://reload.extensions`.
- push: remote is `https://github.com/FahadBinHussain/imgvault.git` (capital F/B). token via rule 34 (Read-VaultSecret, github.com* pattern — never use a token.txt; github tokens are vault-native). `git push "https://x-access-token:$tok@github.com/FahadBinHussain/imgvault.git" main`.
- terabox video provider (2.9.0, 2026-08-27): `TeraBoxUploader` in uploaders.js implements the PCS chunked upload protocol (precreate → locateupload → superfile2 chunks at 4MB → create), cookie auth (`ndus`+`browserid`+`lang` from the logged-in session via `chrome.cookies.getAll({domain:'terabox.com'})`, optional `teraboxCookie` settings override). jsToken is scraped from the www.terabox.com homepage **with a bare UA fetch — no session cookie and no Referer header** (the cookie OR a `www.terabox.com/` Referer redirects to a `simple-verify` captcha gate that has no jsToken; only the bare fetch returns the landing page with the `fn("...")` jsToken wrapper — verified 2026-08-28; the same-page Referer trick does NOT work, 2.11.9→2.11.10). Auto-refreshed on `errno 4000023`. **API calls stay on dm.terabox.com** — only the token scrape uses www (2.11.8; the intermediate 2.11.7 moved the whole base to www and broke `/api/list` with `errno -6`/0-found). 2.11.9 removed the Cookie header from the token scrape to avoid the captcha redirect. storage uses `extra_metadata.videoHosts.terabox` (no dedicated schema column, unlike filemoon/udrop) — the generic `normalizeVideoHosts` round-trips it fine. note: terabox large-file downloads are CDN-throttled (~30KB/s), so it's an upload host; the download dlink comes from `/api/filemetas?dlink=1&origin=dlna` (crack mode). `plan-terabox-vault.md` has the full investigation.
- the CI workflow (`.github/workflows/nextgen-extension-crx.yml`) must reference `manifest.json` as `public/manifest.json` (5 spots: extension version read, copy step, zip name, crx name, native-host version read) — the root `nextgen-extension/manifest.json` was removed in 2.1.7 and every build failed with "Cannot find module './manifest.json'" until fixed (commit 7412db6). vite already copies `public/` into dist, so the workflow's manual `cp` only needs the manifest path corrected.
- vault items are soft-deleted to trash (un-vault + moveToTrash with `skipCollectionCount: true`); trash cards fail gracefully via onError placeholders + 12s timeout.
- resolve page integrity checks (udrop/filemoon) must merge `vaultImages` with `images`: `useImages` filters out vaulted items, so without the merge their codes never count as referenced and their files show up as false orphans on the integrity tabs (was a real bug 2.1.3).
- `retryVideoHostUpload` iterates ALL fallback source candidates until one returns a real video blob — watch pages (text/html) and expired direct links are common, so the retry must never stop at the first candidate (was a real bug 2.1.6). filemoon `/d/`/`/e/` URLs only serve HTML: resolve them via `api.byse.sx/file/direct_link` (`getFilemoonDirectLink`) and fetch the CDN url with the `https://filemoon.sx/` referer (2.1.7). if the account key lacks direct_link permission (`Byse /file/direct_link rejected: Invalid operation`) or hls/link requires Premium API (`This function is not allowed because you've not enabled Premium API`), the anonymous SPA player flow still works and is the reliable path (2.2.0): `filemoonSpa.js` does `POST /api/videos/{code}/captcha` -> solve local proof-of-work (custom ARX hash on SHA-256 constants, ported from the site's pow-*.js bundle: `powHash(nonce:counter)` with leading-zero-bits >= difficulty) -> `POST /api/videos/{code}/captcha/verify` (X-Captcha-Token not needed here) -> `POST /api/videos/{code}/playback` with a dummy `{fingerprint:{token,viewer_id,device_id,confidence}}` + `X-Captcha-Token: <verify token>` -> AES-256-GCM decrypt (WebCrypto; key = base64 key_parts selected by version map `n -> [n, 31-n]`, out of range = all parts; tag appended to payload) -> `sources[]` HLS m3u8 signed URL -> `downloadHlsAsVideoBlob`. the /d/ download page itself is NOT scriptable (countdown + recaptcha + fingerprint attestation), and yt-dlp refuses filemoon outright (`[Piracy] this website is no longer supported`), so player-flow HLS is the only automated recovery path. verified end-to-end 2026-08-15 against filecode z10yjnr2i3ch (segment `seg-1-v1-a1.ts`, 150776 bytes, MPEG-TS).
- manifest source of truth is `nextgen-extension/public/manifest.json`; vite copies it into dist, and postbuild.ps1 must copy from `public/` — the old root `manifest.json` was stale at 2.0.0 and silently overwrote dist on every build (removed; postbuild fixed 2.1.7). if the loaded extension version on edge://extensions doesn't match the manifest, check dist/manifest.json first.
- byse `/file/list` caps at 100 files per page and does NOT send a `total` field — the count is `result.results_total` (also `results`/`pages`). reading `.total` makes pagination stop at page 1, so once the account passes 100 files every healthy video beyond the first page shows up as broken on the resolve integrity check and the page-2+ files vanish from `extra`. fixed 2.2.4 in `listAllFilemoonFiles`; keep the `files.length < perPage` break guard if the API ever stops reporting totals. verified live: 111 files, page 2 returns the remaining 11.
- TeraBox `/api/list` has the SAME 100-per-page cap, and `listTeraBoxFolder` (teraBoxApi.js) originally fetched only `num:100,page:1` — once the account passed 100 files, everything beyond page 1 showed as "broken links" on the resolve integrity check while still playing fine (files existed, just never listed). fixed 2.11.19: paginate until a page returns `< num` (with a `page > 100` safety break). the `[teraBoxApi] Listed N TeraBox files.` console log printing exactly `100` is the tell — the DB has more files than that.
- ukdevilz.com mirrors VK videos; its own `videofile/{id}.mp4` is stale (Cloudflare challenge/404) and generic-extractor downloads fail. `rewrite_mirror_url()` in main.rs rewrites `/watch/{owner_id}_{video_id}` to `vk.com/video-{owner}_{video}` so yt-dlp uses its vk extractor. id format is `owner_video` with an underscore — the id filter must allow `_` (was missed once). apply to both download paths if adding url handling. same trick likely works for other vk mirrors.
- `--impersonate chrome` is added for all downloads (tiktok + generic hosts).
- host survives extension reloads: the native host is single-threaded (download runs inline in the message loop), so when the extension port dies mid-download it never notices until the download finishes — the file still completes in the background. the host writes a completion journal (`%TEMP%\imgvault-yt-dlp-journal-{requestId}.json` with status completed/failed) after every download; on startup the service worker reads it via the `read_download_journal` host action and adopts the real outcome (`completed` resumes the pending auto-upload flow). if the journal is missing the original host is still busy — the record stays `running` with `recoveredFromReload: true` and HostPage polls the journal every 5s. `delete_download_journal` also cleans the pid file. this is the only correct recovery path — never mark a reloaded download `interrupted` while a journal could still appear.

- vault upload progress-log cadence (2.8.0, 2026-08-26): the in-page `uploadVaultedDirectly` progress callback MUST gate its log line on BYTES (`loaded - lastLoggedBytes >= ~20MB`), never on percent or on a string `pct`. percent-gating silently drops every log line between 0% and 100% for files >~1GB (10% of 1.2GB = 128MB = ~39s of silence at ~3.3MB/s), so the live log looks frozen at "0% (363 KB / 1.2 GB)" while the upload actually runs. a progress callback that builds a display label first is the classic trap (string `pct` -> `pct - uploadLogPct` = NaN -> log never fires). context: `✓` rows come from the actual DB — 82 `.mkv` (video/matroska) + 17 `.mp4` on all three hosts; `.bin` on UDrop is the encrypted vault blob (`encryptAndUploadVaultedBlob`, background.js:1146). filemoon is a video-only host, so non-video = `✗`. - **vault streaming (2.12.8/2.12.9, 2026-08-31)**: vaulted video previews no longer download+decrypt the whole blob — the SW serves the DECRYPTED media over HTTP Range so playback/seek needs only the covering chunks. blob layout = 16-byte header `"IVG1"` + uint64le(plaintext total) + uint32le(chunkSize, 8MiB), then per chunk 12-byte IV + AES-256-GCM ciphertext(+16 tag); chunk `i` encrypted offset = `16 + i*(12+chunkSize+16)`. helpers in vaultCrypto.js: `parseVaultBlobHeader`, `getVaultChunkLayout`, `decryptEncryptedChunk`. background `handleVaultStreamRequest(request, itemId)` (registered in the SW `fetch` listener under `^/vault-stream/([^/]+)$`) reads the 16-byte header via a ranged fetch, returns 206 + Content-Range for Range requests (or the whole body for non-Range), and streams `Uint8Array`s through a ReadableStream, decrypting only covering chunks. **2.12.9 — NO Neon DB read per Range request**: `handleVaultStreamRequest` must NEVER call `getImageById(itemId)` — a video player issues ~1 range request per second and each DB round-trip stalls playback ("player shows but loads forever"). the SW builds the item context from URL query params instead: VaultPage `getVaultStreamUrl(item)` embeds `copies` (JSON array of `{host, encryptedBlobUrl, encryptedBlobFileId}`), `mime`, `name` in the stream URL; the handler falls back to the DB item ONLY when `copies` is absent (legacy URLs). also add a 30s overall `Promise.race` timeout around `handleVaultStreamRequest` in the fetch listener and a 30s per-chunk timeout around each `fetchVaultBlobRange` so a stalled host fails loudly instead of hanging the player. udrop/terabox both honor Range (`Accept-Ranges: bytes`, 206) — streaming depends on it. when the stored `encryptedBlobUrl` is the udrop WATCH url (serves HTML at 200), range reads must resolve a fresh signed download URL first (`getFreshVaultStreamUrl`, cached per `${item.id}:${host}`); the DB item still needs `vaultStreamUrlCache` so a freshly uploaded vaulted item streams without restarting the SW.
- **vault-stream terabox 403 + format error root cause (2.12.15, 2026-09-01)**: the 2.12.10-2.12.14 chain fixed cookies + pre-resolve but the video STILL died with `MEDIA_ELEMENT_ERROR: Format error` after `[Vault-stream] layout ok` + `chunk 0 fetch 16 8388636` and 4× `dm-d.terabox.com/file/... 403` in the network log. root cause: **terabox dm-d dlna dlinks are SINGLE-USE** — each signed URL serves ONE request, so the header read (range 0-15) consumes the pre-resolved fresh dlink and the chunk read (range 16-8388651, the whole 8MiB chunk) of the SAME URL 403s. the `fresh`-flag shortcut in `getFreshVaultStreamUrl` (`if (copy.fresh && copy.encryptedBlobUrl) return copy.encryptedBlobUrl`) made the retry in `fetchVaultBlobRange` re-fetch the exact same consumed URL, so every copy failed. ALSO: terabox CDN throttles to ~30KB/s (plan-terabox-vault.md), so an 8MiB encrypted chunk needs ~280s — the 30s per-chunk and 30s outer fetch-listener timeouts would kill even a *working* stream. fix (2.12.15): `getFreshVaultStreamUrl` gained a `forceResolve` option; `fetchVaultBlobRange` now passes `{ forceResolve: true }` for terabox copies so EVERY byte-range read (header + each chunk) resolves a genuinely fresh signed URL via `resolveTeraBoxPlaybackUrl` instead of reusing the consumed one. chunk timeout is host-aware: terabox = 15min (30KB/s × 8MiB ≈ 280s + resolve margin), udrop = 30s. outer fetch-listener race is host-aware: terabox = 20min, others = 5min (300s, generous enough for any slow host without hiding a truly stalled handler). `resolveTeraBoxPlaybackUrl` now caches `fs_id → path` in a module-level `_teraBoxFsPathCache` (teraBoxApi.js) so the per-chunk fresh resolve skips the slow full-root-folder pagination (which was the other 30s+ sink) and hits `/api/filemetas` directly — the vault blob file doesn't move, so the path is stable for the SW session. NOTE: even with the fix, terabox vault streaming is SLOW (30KB/s CDN cap) — a 1GB blob ≈ 9h to stream. if the fix regresses, check the `isTeraBox` detection: `handleVaultStreamRequest` sets `chunkTimeoutMs = isTeraBox ? 15min : 30s` from the `copies` query param, and the outer listener race parses the same `copies` param — both must agree on what counts as a terabox copy (host lowercased === 'terabox').
- **vault-stream terabox SPEED root cause (2.12.16, 2026-09-01)**: even with forceResolve, terabox vault streaming was still stuck at ~30KB/s (1MB range took 71.6s, measured with curl). the user correctly reported "gallery terabox items is more faster" and "make it like the rclone alist". investigation: measured the same 1.3GB blob through AList+rclone → **0.68 MB/s sustained** (60s test, single connection via `rclone cat --multi-thread-streams 1`). compared direct dlna dlink fetch with cookie vs without: dlink redirect WITHOUT cookie → `tsl=2000&csl=2000` in the CDN URL, 0.68MB/s download; WITH cookie → `tsl=30&csl=30`, 0.01MB/s. **the CDN throttle is triggered by the logged-in account cookie.** the 2.12.10 "cookie fix" (adding Cookie+Referer to dlink range reads) was backwards — it made the CDN identify the request as the free-tier account and apply the 30KB/s cap. the gallery plays fast because the browser's `<video>` in the extension page is cross-origin to terabox.com, so SameSite/Lax drops the cookie → tsl=2000. fix (2.12.16): removed the Cookie header from dlink range reads in `fetchVaultBlobRange` for terabox copies. also removed the now-dead `getTeraBoxRangeCookie` method. the dlink itself is a signed CDN URL that works without cookies (tested: 8MiB range read, no cookie, 0.68MB/s, works for repeated reads on the same dlink). forceResolve (fresh dlink per chunk) is retained as a safety net but the speed win is entirely from dropping the cookie. keep `User-Agent` and `Referer` headers — they don't trigger throttle.

- **CRITICAL: credentials omit for terabox dlink fetch (2.12.17, 2026-09-01)**: removing the explicit Cookie header (2.12.16) was NOT enough - Chrome SW with <all_urls> auto-attaches site cookies to fetch() even without explicit Cookie header, so the CDN still saw the session cookie -> tsl=30. the real fix: credentials:'omit' on the dlink fetch(url, { headers, credentials: 'omit' }). this forces Chrome to send NO credentials regardless of host permissions. apply to BOTH the primary and retry fetch in fetchVaultBlobRange. the gallery <video> gets no cookie because extension page is cross-origin to terabox.com (SameSite=Lax drops it) -> tsl=2000. never send the cookie explicitly - that triggers the throttle.
