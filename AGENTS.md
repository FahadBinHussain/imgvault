# imgvault

chrome extension (mv3, no build for ext itself; vite build outputs to `dist/`) + tauri rust native host for yt-dlp downloads.

- native host source: `native-host/src-tauri/src/main.rs`; build with `cargo build --release --target x86_64-pc-windows-gnu` and copy the exe to `native-host/ImgVault-Native-Host.exe`; rebuild + copy after every rust change, not just compile.
- extension edits: bump `"version"` in `nextgen-extension/public/manifest.json`, run `pnpm build`, then `start msedge http://reload.extensions`.
- push: remote is `https://github.com/FahadBinHussain/imgvault.git` (capital F/B). token via rule 34 (Read-VaultSecret, github.com* pattern — never use a token.txt; github tokens are vault-native). `git push "https://x-access-token:$tok@github.com/FahadBinHussain/imgvault.git" main`.
- terabox video provider (2.9.0, 2026-08-27): `TeraBoxUploader` in uploaders.js implements the PCS chunked upload protocol (precreate → locateupload → superfile2 chunks at 4MB → create), cookie auth (`ndus`+`browserid`+`lang` from the logged-in session via `chrome.cookies.getAll({domain:'terabox.com'})`, optional `teraboxCookie` settings override). jsToken is scraped from the www.terabox.com homepage **with a bare UA fetch — no session cookie and no Referer header** (the cookie OR a `www.terabox.com/` Referer redirects to a `simple-verify` captcha gate that has no jsToken; only the bare fetch returns the landing page with the `fn("...")` jsToken wrapper — verified 2026-08-28; the same-page Referer trick does NOT work, 2.11.9→2.11.10). Auto-refreshed on `errno 4000023`. **API calls stay on dm.terabox.com** — only the token scrape uses www (2.11.8; the intermediate 2.11.7 moved the whole base to www and broke `/api/list` with `errno -6`/0-found). 2.11.9 removed the Cookie header from the token scrape to avoid the captcha redirect. storage uses `extra_metadata.videoHosts.terabox` (no dedicated schema column, unlike filemoon/udrop) — the generic `normalizeVideoHosts` round-trips it fine. note: terabox large-file downloads are CDN-throttled (~30KB/s), so it's an upload host; the download dlink comes from `/api/filemetas?dlink=1&origin=dlna` (crack mode). `plan-terabox-vault.md` has the full investigation.
- the CI workflow (`.github/workflows/nextgen-extension-crx.yml`) must reference `manifest.json` as `public/manifest.json` (5 spots: extension version read, copy step, zip name, crx name, native-host version read) — the root `nextgen-extension/manifest.json` was removed in 2.1.7 and every build failed with "Cannot find module './manifest.json'" until fixed (commit 7412db6). vite already copies `public/` into dist, so the workflow's manual `cp` only needs the manifest path corrected.
- vault items are soft-deleted to trash (un-vault + moveToTrash with `skipCollectionCount: true`); trash cards fail gracefully via onError placeholders + 12s timeout.
- resolve page integrity checks (udrop/filemoon) must merge `vaultImages` with `images`: `useImages` filters out vaulted items, so without the merge their codes never count as referenced and their files show up as false orphans on the integrity tabs (was a real bug 2.1.3).
- `retryVideoHostUpload` iterates ALL fallback source candidates until one returns a real video blob — watch pages (text/html) and expired direct links are common, so the retry must never stop at the first candidate (was a real bug 2.1.6). filemoon `/d/`/`/e/` URLs only serve HTML: resolve them via `api.byse.sx/file/direct_link` (`getFilemoonDirectLink`) and fetch the CDN url with the `https://filemoon.sx/` referer (2.1.7). if the account key lacks direct_link permission (`Byse /file/direct_link rejected: Invalid operation`) or hls/link requires Premium API (`This function is not allowed because you've not enabled Premium API`), the anonymous SPA player flow still works and is the reliable path (2.2.0): `filemoonSpa.js` does `POST /api/videos/{code}/captcha` -> solve local proof-of-work (custom ARX hash on SHA-256 constants, ported from the site's pow-*.js bundle: `powHash(nonce:counter)` with leading-zero-bits >= difficulty) -> `POST /api/videos/{code}/captcha/verify` (X-Captcha-Token not needed here) -> `POST /api/videos/{code}/playback` with a dummy `{fingerprint:{token,viewer_id,device_id,confidence}}` + `X-Captcha-Token: <verify token>` -> AES-256-GCM decrypt (WebCrypto; key = base64 key_parts selected by version map `n -> [n, 31-n]`, out of range = all parts; tag appended to payload) -> `sources[]` HLS m3u8 signed URL -> `downloadHlsAsVideoBlob`. the /d/ download page itself is NOT scriptable (countdown + recaptcha + fingerprint attestation), and yt-dlp refuses filemoon outright (`[Piracy] this website is no longer supported`), so player-flow HLS is the only automated recovery path. verified end-to-end 2026-08-15 against filecode z10yjnr2i3ch (segment `seg-1-v1-a1.ts`, 150776 bytes, MPEG-TS).
- manifest source of truth is `nextgen-extension/public/manifest.json`; vite copies it into dist, and postbuild.ps1 must copy from `public/` — the old root `manifest.json` was stale at 2.0.0 and silently overwrote dist on every build (removed; postbuild fixed 2.1.7). if the loaded extension version on edge://extensions doesn't match the manifest, check dist/manifest.json first.
- byse `/file/list` caps at 100 files per page and does NOT send a `total` field — the count is `result.results_total` (also `results`/`pages`). reading `.total` makes pagination stop at page 1, so once the account passes 100 files every healthy video beyond the first page shows up as broken on the resolve integrity check and the page-2+ files vanish from `extra`. fixed 2.2.4 in `listAllFilemoonFiles`; keep the `files.length < perPage` break guard if the API ever stops reporting totals. verified live: 111 files, page 2 returns the remaining 11.
- TeraBox `/api/list` has the SAME 100-per-page cap, and `listTeraBoxFolder` (teraBoxApi.js) originally fetched only `num:100,page:1` — once the account passed 100 files, everything beyond page 1 showed as "broken links" on the resolve integrity check while still playing fine (files existed, just never listed). fixed 2.11.19: paginate until a page returns `< num` (with a `page > 100` safety break). the `[teraBoxApi] Listed N TeraBox files.` console log printing exactly `100` is the tell — the DB has more files than that.
- ukdevilz.com mirrors VK videos; its own `videofile/{id}.mp4` is stale (Cloudflare challenge/404) and generic-extractor downloads fail. `rewrite_mirror_url()` in main.rs rewrites `/watch/{owner_id}_{video_id}` to `vk.com/video-{owner}_{video}` so yt-dlp uses its vk extractor. id format is `owner_video` with an underscore — the id filter must allow `_` (was missed once). apply to both download paths if adding url handling. same trick likely works for other vk mirrors.
- `--impersonate chrome` is added for all downloads (tiktok + generic hosts).
- host survives extension reloads: the native host is single-threaded (download runs inline in the message loop), so when the extension port dies mid-download it never notices until the download finishes — the file still completes in the background. the host writes a completion journal (`%TEMP%\imgvault-yt-dlp-journal-{requestId}.json` with status completed/failed) after every download; on startup the service worker reads it via the `read_download_journal` host action and adopts the real outcome (`completed` resumes the pending auto-upload flow). if the journal is missing the original host is still busy — the record stays `running` with `recoveredFromReload: true` and HostPage polls the journal every 5s. `delete_download_journal` also cleans the pid file. this is the only correct recovery path — never mark a reloaded download `interrupted` while a journal could still appear.

- resolve page notices render on the videos tabs ONLY when `notice.type === 'error'` (success messages from "Link to item" were invisible), and the link handlers set the success notice BEFORE `run*IntegrityCheck()`, which starts with `setNotice(null)` and wipes it. fixed 2.2.7: notices render for any type on both video tabs, and the success notice is set AFTER the check re-run. link flow writes `filemoon_watch_url=https://filemoon.sx/d/{code}` + `filemoon_direct_url=https://filemoon.sx/e/{code}` (udrop: `https://www.udrop.com/file/{code}` both) via `updateImage`.
- after "Link to item" the re-run check used STALE `images`/`vaultImages` hook state — the just-linked item still lacked the URL in memory, so the orphan stayed listed right after linking (and external DB edits like psql links show as false orphans until page refresh). 2.2.8 added `Promise.all([reloadImages({ silent: true }), reloadVaultImages()])` after `updateImage`, but the orphan STILL persisted even with the write landing in Neon — the running extension simply wasn't the new build (the `http://reload.extensions` reload hadn't taken; always verify the loaded version on edge://extensions matches dist/manifest.json). fixed properly in 2.2.9: `runFilemoonIntegrityCheck`/`runUdropIntegrityCheck` now fetch FRESH items themselves (`sendMessage('getImages')` + `sendMessage('getVaultImages')`) instead of trusting hook state, so every check run sees current DB state regardless of page state or build-timing.

- vault encryption (2.6.0, 2026-08-25): `vaultCrypto.js` (pure WebCrypto AES-256-GCM + PBKDF2 + key wrapping), `vaultSession.js` (page-side key in memory), `vaultSetMasterKey`/`vaultClearMasterKey` SW messages, `handleVaultedUpload` encrypts before upload, `moveItemToVault` encrypts on move (requires unlock; throws if locked), `restoreFromVault` decrypts -> re-uploads via normal providers, `decryptVaultBlob` regenerates stale udrop download URLs from fileId. legacy vaults auto-upgrade on first unlock. legacy vaulted items (pre-2.6.0) stay unencrypted per option B. `plan.md` has the full architecture.
- vault upload progress-log cadence (2.8.0, 2026-08-26): the in-page `uploadVaultedDirectly` progress callback MUST gate its log line on BYTES (`loaded - lastLoggedBytes >= ~20MB`), never on percent or on a string `pct`. percent-gating silently drops every log line between 0% and 100% for files >~1GB (10% of 1.2GB = 128MB = ~39s of silence at ~3.3MB/s), so the live log looks frozen at "0% (363 KB / 1.2 GB)" while the upload actually runs. a progress callback that builds a display label first is the classic trap (string `pct` -> `pct - uploadLogPct` = NaN -> log never fires). ALSO: udrop accepts large single PUTs fine — verified 50MB=13.5s, 512MB=195s, 1.2GB=387s (~3.3MB/s), all through `POST /api/v2/file/upload` with `upload_file` FormData. there is NO per-upload size cap on the server for a single request; the "stuck upload" symptom is a CLIENT log-timing illusion. udrop `api/v2` has no working `file/list` method (only `file/delete`) — file enumeration isn't available via API, so vault orphan cleanup must use file_ids captured from upload responses.
- **STRICT provider symmetry — no fallbacks (2.11.x)**: user forbids fallback chains for anything. resolve every provider-derived value (video playback, modal source, poster/thumbnail, images) ONLY through the host selected in settings (`defaultVideoSource` / `defaultGallerySource`) via `getStrictVideoProviderLink` / `getStrictImageProviderLink`. never use the chain-based `getPreferredVideoProviderLink` / `getPreferredImageProviderLink` for UI. empty poster when the selected host has no thumbnail (udrop/terabox have none) — don't backfill from another host.

## video hosts — file type support matrix (literal, evidence-backed)

status legend (apply everywhere in this repo): `✓` = proven/works (observed in DB or a real run), `✗` = structurally won't accept (video-only host, etc.), `?` = not tested yet — never assume `?` means yes or no, and mark results back here after a test fills one.

| `.webm` | ? | ? | ? |
| `.mov` | ? | ? | ? |
| `.avi` | ? | ? | ? |
| `.ts` | ? | ? | ? |

context: `✓` rows come from the actual DB — 82 `.mkv` (video/matroska) + 17 `.mp4` on all three hosts; `.bin` on UDrop is the encrypted vault blob (`encryptAndUploadVaultedBlob`, background.js:1146). filemoon is a video-only host, so non-video = `✗`. TeraBox `.bin` marked `✓` 2026-08-30: the PCS precreate API accepted the `.bin` filename (responded `4000023` need-verify/auth-only — stale cookie — never a file-type rejection), and PCS is byte-agnostic: it never checks extensions at precreate/create, it just uploads bytes. every other extension is untested (`?`) — fill them with real uploads, not guesses.
- **vault host selection (2.12.0, 2026-08-30)**: the vault blob target, move-to-vault source, and restore target are now user-selectable (was hardcoded UDrop). `selectedVaultHost` (chrome.storage.local, default `'udrop'`, `'udrop'|'terabox'`) = where the encrypted `.bin` lives; stored as `vaultHost` on the vaulted item (round-trips via extra_metadata, no schema change). `encryptAndUploadVaultedBlob(blob, meta, onProgress, vaultHost)` dispatches to UDropUploader or TeraBoxUploader (fetch-based, SW-safe). `decryptVaultBlob`/`resolveVaultDownloadUrl(url, fileId, vaultHost, fileName)` regenerate the correct host's download URL (udrop `/file/download` vs terabox `resolveTeraBoxPlaybackUrl` dlink). `moveItemToVault(id, {sourceHost, vaultHost})` uses the STRICT source-host link (`getStrictVideoProviderLink`/`getStrictImageProviderLink`) — no hardcoded fallback chain; throws if the picked host has no link. `restoreFromVault(id, {targetHostKeys})` filters restore targets by the picker (defaults to all configured when omitted). UI: GalleryPage upload modal shows a UDrop/TeraBox vault blob host picker when `uploadToVault`; new `VaultMoveModal` component (source host + blob host) for single/bulk move-to-vault; VaultPage restore shows an `UploadHostSelector` (`selectedRestoreHostKeys`). legacy vaulted items without `vaultHost` decrypt as udrop. **2.12.4/2.12.5 catalog-driven vault hosts**: never hardcode the vault blob host list/labels in UI or dispatch code — they come from `providerCatalog.js`. `getVaultBlobHostServices()` returns ALL video services (2.12.5 dropped the `vaultBlobHost` filter), so every video host is selectable as the encrypted-blob target and shows up in the VaultMoveModal + GalleryPage pickers automatically; `getVaultBlobHostOptions()` gives the picker list; `DEFAULT_VAULT_BLOB_HOST` is the storage default. each service supplies `uploaderClass` (page-side construction) and optional `vaultDownloadUrl` (fresh download URL regen — absent = falls back to the stored URL). background `encryptAndUploadVaultedBlob`/`resolveVaultDownloadUrl`/GalleryPage direct vault upload all dispatch through the catalog service by key — no host-name branches. add a new host by adding a VIDEO_UPLOAD_SERVICES entry with `uploaderClass` (+ `vaultDownloadUrl` when it needs fresh-URL regen) — no other code changes.
- **vault restore bug (2.12.1, 2026-08-30)**: two-part bug where "Restore to Gallery" showed instantly but the item stayed in the vault. (1) `this.teraboxUploader` was NEVER instantiated in the background constructor (only pixvid/imgbb/filemoon/udrop were), so the restore loop `this[service.uploaderKey]` found `undefined` for terabox, silently skipped it, ended with empty upload results, and threw → fell back to legacy flag-only restore (no actual upload). fixed: `this.teraboxUploader = new TeraBoxUploader()` in the constructor. (2) even the legacy flag-only restore couldn't clear `isVaulted`: `buildExtraSeed` in `shared/mediaDbPayload.js` (and its vendored copy `web/src/shared/mediaDbPayload.js`) spread `sourceExtra` (the stale DB extra_metadata with `isVaulted: true`) LAST, clobbering the explicit `isVaulted: false` update. fixed: only carry over extra-only keys not already present at top level (`extraOnly` filter), so explicit top-level updates win. both files must stay in sync.
- **NEVER `await import()` a chunk from the MV3 service worker (2.12.3, 2026-08-30)**: Vite's dynamic-import runtime (`dist/assets/preload-helper-*.js`) calls `document`/`window` APIs; in a SW neither exists, so a failed or even a *successful* dynamic import that hits the preload-error path throws `ReferenceError: window is not defined` — the restore path got this as "Restore failed: Vault restore failed: Vault restore failed: window is not defined". the encrypt/decrypt vault functions were split into `vaultCrypto-*.js` because `decryptBlob`/`decryptMetadata` were imported with `await import('../utils/vaultCrypto.js')` inside `decryptVaultBlob` and `restoreFromVault`. fix: statically import ALL vaultCrypto functions in background.js (decryptBlob/decryptMetadata were missing from the static import that already had encryptBlob/encryptMetadata), and remove the two dynamic imports. static imports bundle into the SW module graph and always work; dynamic imports route through the window-reliant preload helper. same applies to any other runtime `import()` in background.js (sceneFileCache.js still uses it — scene save/load will hit the same bug; convert to static import if that flow matters).
- **vault restore silent half-restore bug (2.12.2, 2026-08-30)**: "Restore to Gallery" showed success but the item had NO playable URL — symptom: DB row with `isVaulted:false` in extra_metadata but `encryptedBlobUrl`/`encryptedMetadata`/`encryptedBlobFileId` still present and all provider URL columns empty, file_name still `*.bin`. root cause: MV3 SW idle-restart wipes the in-memory `this.vaultMasterKey` (background.js constructor resets it to null); the page's session-restore only checked `sessionStorage.passHash === config.passHash` and set `unlocked=true` WITHOUT re-sending the key to the SW, so `restoreFromVault`'s `if (current.encryptedBlobUrl && this.vaultMasterKey)` was false and it SILENTLY fell into the legacy flag-only restore (just flips isVaulted, no decrypt/re-upload). fixed two ways: (1) VaultPage `unlockWithPasscode` now stores `keyB64` in sessionStorage alongside passHash, and the session-restore block rehydrates both page (`importMasterKeyFromB64`) and SW (`vaultSetMasterKey`) keys when the session is valid; (2) `restoreFromVault` now FAILS LOUDLY (`throw new Error('Vault is locked. Unlock the vault before restoring this encrypted item.')`) when `current.encryptedBlobUrl` exists but the SW key is missing — it can no longer silently legacy-restore an encrypted item. repair path for a half-restored item: set it back to vaulted in the DB (`extra_metadata = extra_metadata || '{"isVaulted": true, "vaultMode": "hidden", "vaultedAt": "<now>"}'::jsonb`) then restore it again with the vault unlocked. sessionStorage holds the raw keyB64 tab-scoped — acceptable (same trust as passHash), cleared on tab close / lockVault.
- **vault streaming (2.12.8/2.12.9, 2026-08-31)**: vaulted video previews no longer download+decrypt the whole blob — the SW serves the DECRYPTED media over HTTP Range so playback/seek needs only the covering chunks. blob layout = 16-byte header `"IVG1"` + uint64le(plaintext total) + uint32le(chunkSize, 8MiB), then per chunk 12-byte IV + AES-256-GCM ciphertext(+16 tag); chunk `i` encrypted offset = `16 + i*(12+chunkSize+16)`. helpers in vaultCrypto.js: `parseVaultBlobHeader`, `getVaultChunkLayout`, `decryptEncryptedChunk`. background `handleVaultStreamRequest(request, itemId)` (registered in the SW `fetch` listener under `^/vault-stream/([^/]+)$`) reads the 16-byte header via a ranged fetch, returns 206 + Content-Range for Range requests (or the whole body for non-Range), and streams `Uint8Array`s through a ReadableStream, decrypting only covering chunks. **2.12.9 — NO Neon DB read per Range request**: `handleVaultStreamRequest` must NEVER call `getImageById(itemId)` — a video player issues ~1 range request per second and each DB round-trip stalls playback ("player shows but loads forever"). the SW builds the item context from URL query params instead: VaultPage `getVaultStreamUrl(item)` embeds `copies` (JSON array of `{host, encryptedBlobUrl, encryptedBlobFileId}`), `mime`, `name` in the stream URL; the handler falls back to the DB item ONLY when `copies` is absent (legacy URLs). also add a 30s overall `Promise.race` timeout around `handleVaultStreamRequest` in the fetch listener and a 30s per-chunk timeout around each `fetchVaultBlobRange` so a stalled host fails loudly instead of hanging the player. udrop/terabox both honor Range (`Accept-Ranges: bytes`, 206) — streaming depends on it. when the stored `encryptedBlobUrl` is the udrop WATCH url (serves HTML at 200), range reads must resolve a fresh signed download URL first (`getFreshVaultStreamUrl`, cached per `${item.id}:${host}`); the DB item still needs `vaultStreamUrlCache` so a freshly uploaded vaulted item streams without restarting the SW.
